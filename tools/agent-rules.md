# Development skills (devskills)
For every development task or ticket — requirement analysis, feasibility, impact, spec, code, tests, review, commit — invoke the `dev-orchestrate` skill first and follow its skill routing: before working on an area, load every domain skill whose area the task touches (database/deletes/locks → change-database, endpoints → design-api, jobs/external calls → design-reliability, tests → test-safely, reviewing a diff/PR or your own change → review-code, …), even for small changes, specs and reviews. End with "Skills applied" and their rule IDs.

Cloud access (OPS-011): never independently connect to a cloud account or use any cloud profile, secret key, access key, token, service account, SSO session or ambient credentials. Before each cloud command/tool action (or an explicitly listed batch), show a warning with the exact action, account/profile, environment, target and risks/costs; wait for the user's explicit approval covering those actions. This includes read-only list/get/describe, identity checks, login, connection tests and remote plans/dry runs, through CLI, SDK, scripts, Terraform or MCP, on dev/STG/production and any other cloud environment. Existing credentials, a read-only label and a general request to inspect/test are not approval. Do not connect to discover the account before approval; report unknown target details and clarify them. Keep secrets out of the warning. Only genuinely offline work and credential-free local mocks proceed without cloud approval. Follow dev-orchestrate's authorization reference; stricter user restrictions still apply.

Non-local databases (OPS-012): never independently connect to or perform any operation on a database outside this machine, whether cloud or non-cloud, dev/STG/production or another remote/shared environment. Before each action (or an explicitly listed batch), warn with the exact commands/queries, server/environment, database, purpose and risks, then wait for explicit user approval covering those actions and targets. This includes SELECT, schema/metadata inspection, estimated/actual EXPLAIN, health/connection checks, exports/backups, writes, migrations, restores and maintenance, through CLI, ORM/SDK, apps/scripts/tests, SSH/tunnels, remote Docker/Kubernetes contexts or MCP; an existing session, credentials or a localhost tunnel do not grant permission. Do not connect to identify or validate an unknown target before approval. General inspect/debug/test requests are not approval. Only in-scope work on confirmed local databases and offline review may proceed directly; this overrides read-only exceptions.

Approval dialogs (OPS-013): when approval is missing, use a supported interactive confirmation tool (on this Codex surface: `request_user_input_async`) with a short title containing an icon, action and environment, e.g. `🗄️ Đọc DB · STG` or `☁️ Xem AWS · DEV`; include exact commands/queries, targets, purpose and risks below. Offer refusal first and explicit scoped approval second. A default selection, tool return, dismissal or silence is not consent; async requests stay pending until the user's actual reply. Use only tools whose contracts permit approvals; never change session permissions to force a popup. If no suitable tool is available, explicitly report that limitation and wait for consent in chat. See dev-orchestrate's `references/approval-dialog.md`. A preview never authorizes any cloud or remote DB operation.
